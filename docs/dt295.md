# PIX-DT295 の C 経路

## 状況

PIX-DT295 向けの C 経路は開発中で、確認範囲は macOS `darwin-arm64`・地上波 T27・ターゲット0のみです。実機録画は 15.023 秒、300.023 秒、18,000.003 秒の各段階で正常終了しました。5 時間の保存 TS は 194,054,187 パケット、36,482,187,156 バイトです。全 TS の検査で CC 不連続、TEI、scramble、invalid、section CRC 異常はいずれも 0 件でした。2,543,070 セクションの CRC 検査も失敗 0 件でした。主ストリーム検査では MPEG-2 video / AAC の PID 256 / 272 と H.264 video / AAC の PID 1409 / 1411 を確認しました。これは全 PID の音声を一括して完全デコードしたという意味ではありません。

5 時間中の USB error / timeout は 0 件、最大 USB gap は 173.734 ms でした。保存キューのピークは 9,502,648 バイト（128 MiB 容量の約 7.1%）で、記録末尾に pending / refused / uncertain bytes はありません。5 分録画では一時ピークが 73,007,168 バイトまで増えましたが、録画中に回復して終了時の pending / refused / uncertain bytes は 0 でした。保存遅延の原因は特定していません。

記録中の PID 273 追加を1回確認しました。追加イベントと近傍 PMT は新 PID と空きスロットの割当を示し、既存ルートと ECM の対応を保つソース上の安全判定を通る追加処理が診断イベントとして記録されました。機器レジスターの readback はありません。イベント後の保守的な実測下限は 7,947.878 秒でした。全 TS には PID 273 の 84,482 パケットが含まれ、この範囲も全体の CC / TEI / scramble / invalid 検査で異常 0 件です。section CRC も全体で失敗 0 件でした。追加直後と活動中の有限 65,536 パケット AAC 273 ウィンドウでは完全 PES / ADTS の FFmpeg デコードが通りましたが、PID 273 全体の完全デコードは実施していません。追加後30分と終端の限定窓 では PID 273 と対応 PMT 項目がともに不在でした。追加時と消失時の部分 PES は既知 Issue #2 として残っています。

r8 のソフトウェア検証では native macOS と Linux x64 のテストを実行しました。Linux ARM64、Windows x64、Android の aarch64 / armv7a / x86_64 はクロスビルドとバイナリ形式・依存関係検査のみで、各ターゲットでのテスト実行や実機検証はしていません。CLI、既定機種、終了コード分類、バージョン 0.1.4 は変更していません。これは RC ビルド前の開発検証であり、RC ビルド、配布パッケージ、リリースはまだ作成していません。過去の Python/C 試作の結果は、この製品 C 経路の検査に読み替えていません。

## 衛星（ISDB-S）経路

衛星経路は既存研究のレジスター列をCへ移植したもので、地上波と同じ `dt295.assets` を使います。ただし衛星レジスタ表（driver VA `0x845a0`）は現行bundleに含まれないため、`tools/prepare-dt295-assets.py` でbundleを作り直す必要があります。作り直していないbundleでは衛星tuneは明示エラーになります。地上波経路は従来のbundleで動作します。

衛星はIF周波数（950–2150 MHz）と、明示TSIDまたはslotを指定します。`-c BS1`/`-c CS22` などのチャンネル表記はIF周波数へ変換されます。slotは受信中のdemod `0xCE` から得た8候補（big-endian、0/0xFFFF除外）を使い、`BS01_0` 形式または `--slot 0..7` で指定できます。選択後はE6の読戻しとPAT TSIDを照合し、一致しなければ停止します。

```sh
./pix-ts --model dt295 --assets ./assets --system bs -c BS1 --tsid 16400 -t 10 -o bs.ts
./pix-ts --model dt295 --assets ./assets --system bs -c BS01_0 -t 10 -o bs-slot.ts
./pix-ts --model dt295 --assets ./assets --system cs -c CS22 --tsid 29024 -t 10 -o cs.ts
```

実機ではBS1（TSID 16400）の短時間受信・停止・再取得とT27前後を確認済みです。CS22は衛星tune/lock/PAT/PMTまで確認しましたが、既存の複数独立ECM制限で録画planが停止します。LNB給電、LNA制御、校正dB値、全MUX、長時間・動的PMT追従は対象外です。

## 実行

実機用の `dt295.assets` を `assets/` に用意したうえで、物理チャンネルを `T27` 形式で指定します。

```sh
./pix-ts --model dt295 --assets ./assets -c T27 -t 60 -o capture.ts
```

`--model`を省略した従来の機種はDT181です。`--list`と`--list-json`の機器番号も選択した機種の中で数えます。DT295を列挙する場合は`--model dt295 --list-json`を指定します。既存DT181の引数・既定値・終了コード分類は維持します。

この経路はサービス選択を行わず、PAT/CAT/PMT を追跡して固定長の PID ルート計画を作ります。有限個の専用 PID スロットと一般 PID スロットを使い、ヌル PID は登録しません。全 PMT の完全な取得後に記録を始めます。記録中の追加は、既存の PID・ECM 対応をすべて保ったまま、未登録の non-ECM PID を空きスロットへ登録できる場合に限ります。実機で確認した PID 273 の追加もこの条件です。新たな ECM 登録、既存 PID/ECM の再割当・rebind、primary の置換、空きスロットのない追加など、安全に保持できない変更は拒否して停止します。PMT の通常更新や登録済み PID の一時的な消失だけでは停止理由になりません。

テーブル version は5 bit serialとして限定的に扱います。直前に確定したversionから前向き差分1〜15（31から0へのwrapを含む）は受理し、直前の旧versionの遅延sectionは無視します。それ以外の後退・半周以上の不明な遷移は `unsupported_tables` として停止対象にします。同じ確定versionでCRC正常のsection内容が変わった場合、PMT（table_id 2）に限り新しいsectionを採用してPMT route metadataを再構築します。このケースは `invalid_sections` の診断カウンターを増やします。PAT/CATやPMT再解析に失敗する変更は `unsupported_tables` として拒否します。任意の長期version周回を推測して順序付ける動作ではありません。

初期テーブルでは、各 program-level または elementary-stream-level の CA descriptor 範囲に対応する system 0x0005 の ECM PID は1つまでです。同じ範囲に異なる ECM PID が複数ある PMT は拒否します。さらに初期受信構成全体でも、異なる ECM PID が2つ以上必要な場合は記録開始前に拒否します。複数独立 ECM の同時処理は保証対象外です。

## オンボード H.264 変換（DT295 実験フック）

`dt295/transcode-hooks` ブランチには、DT295 ASSP の既知レジスター列を適用する実験フックがあります。通常の DT295 受信 API や安定版の一般向けプリセット機能ではありません。環境変数を設定しなければ従来の受信挙動を維持します。

- `DT295_XREG`: profile field table の適用直後に追加の masked register writes を適用します。
- `DT295_XREG2`: PID routes と program metadata の設定後、取得開始コマンド直前に最後の出力選択を書きます。
- `DT295_TOLERATE_PSI=1`: 動的受信中の codec metadata 変更を opt-in で許容します。dedicated PID 構成に変更がある場合は拒否します。
- 同一 version の section content rewrite は PMT に限り、新しい section を採用して PMT route metadata を再構築します。PAT/CAT やその他の不明な変更は fail-closed のままです。

`DT295_XREG` / `DT295_XREG2` は `addr:shift:width:value[,addr:...]` 形式です。address/value は hexadecimal、shift/width は decimal です。**profile values、recordings、raw USB captures、keys、IVs、runtime bundle は Git / issue / build artifact に追加しないでください。** 実験 profile は各自のローカル `/config` で管理します。

この legacy capture path を実験ビルドする場合は、capture test define を明示します（Makefile では既定で有効化されません）。

```sh
make -j4 pix-ts-legacy CFLAGS="-O2 -g -DDT295_CAPTURE_TESTING"
```

このフックは release artifact の対応を意味しません。DT295 の変換実機検証では 1280×720 H.264 Main@3.1、約 7.6 Mbps の 20 秒キャプチャと全 4 サイズ/レートの短時間出力を確認しました。録画・profile・asset の実体はリポジトリ外に置いています。

## 入力 bundle の準備

`tools/prepare-dt295-assets.py` は、ユーザーが用意した入力から実行時 bundle を生成します。入力は以下です。

- `--driver`: 正規の `pxmb86m0x_usb.sys`。ツールが対応する公式ファイルを SHA-256 で照合します。
- `--idle` と `--trc`: 対象機器用の idle と地上波 TRC イメージ。
- `--profile`: schema 1 / target 0 のプロファイル JSON。トップレベルに `schema`, `target`, `ts_key_request_words`（uint32 が3個の配列）, `fields`（1件以上の配列）を含めます。各 field 行は `name`, `address`, `shift`, `width`, `value` を持ちます。値は設定レジスター範囲内である必要があります。ツールは `INIT_S_AUTO_PID_MODE` を `0`、`INIT_S_PAYLOAD_UNIT_START_DISABLE_MODE` を `1` に正規化し、入力プロファイルに含まれる PID/ECM ルート関連フィールドを除去してから bundle に保存します。PID/ECM ルートは実行時の PSI から計画します。
- `--iv`: アプリケーションから抽出した TS CBC 用の独立した16バイト IV ファイルです。制御セッション用 IV はドライバー material から別に読み込みます。両者は異なる用途の値で、同一である必要はありません。
- `--output`: 出力先。一般的な配置例は `assets/dt295.assets` です。

```sh
python3 tools/prepare-dt295-assets.py \
  --driver /path/to/pxmb86m0x_usb.sys \
  --idle /path/to/idle-image \
  --trc /path/to/terrestrial-trc \
  --profile /path/to/target-0-profile.json \
  --iv /path/to/iv.bin \
  --output assets/dt295.assets
```

ツールは入力を検証し、6 セクションそれぞれに長さと SHA-256 を付けた bundle を作ります。bundle は個人用の実行時データとして扱ってください。README やログに機微な入力内容、鍵素材、IV、bundle のバイト列や値を記載しないでください。テスト用の bundle は合成データのみを使用します。

## 配布パッケージ

通常のバイナリ package には DT181 の3資産だけが含まれます。非公開リリースを手動で最終化するときに `--dt295-assets` を指定した場合だけ、最終化スクリプトが妥当性を検査し、`darwin-arm64` バイナリ package の `assets/dt295.assets` に追加します。ソース package には追加しません。

```sh
python3 tools/finalize-private-release.py /path/to/dt181-assets \
  --dt295-assets assets/dt295.assets
python3 tools/verify-release.py --with-assets --with-dt295-assets
```

これはオプションの packaging 経路の説明であり、現在のリリースに DT295 bundle が含まれることを示すものではありません。ここでは実機用 bundle を処理したり、リリースを発行したりしません。

## 出力と既知の制約

出力に詰まりが続く場合、pipe は3秒、ファイル出力は30秒で失敗扱いにします（ファイル出力は10秒で警告）。停止後の出力 drain は最大60秒です。これらはソフトウェア上の待機期限であり、OS がブロックした通常ファイル書き込みに対するポータブルな強制終了保証ではありません。

状態ログは USB 完了・消費バイト、後着バイト、保留転送、保存の確定・拒否・不明バイトを分けます。停止要求後の drain と cancel 中の後着入力は録画時間外であり、TS 全件保存に含めません。USB callback が期限内に回収できない場合は機器や転送バッファを解放せず、異常終了として記録します。

既知 Issue #2 の追加音声 PID の出現・消失境界で部分 PES が残る問題は未解決です。PID 273 については有限ウィンドウでの PSI / PES / ADTS 検査と、活動中に得られた完全フレームのデコードは通りました。一方、PMT が PID 273 を含む期間と含まない期間の境界には部分 PES が確認されており、全 PID 273 の完全デコードを示すものではありません。端数・部分 PES を一般に許容する例外や、PID 273 だけを除外する扱いはありません。Issue #2 は引き続き追跡します: [Issue #2](https://github.com/Khronos31/pix-userland/issues/2)。

検査上の限界: 保存 TS の SHA-256 は保存後のファイル読み出しに対する値で、実行中に USB 入力全体を独立してハッシュしたものではありません。保存 TS 用 C チェッカーは実行時と同じ実装を使い、section parser と FFmpeg が補助的な検査を加えます。raw USB 入力は保存しておらず、独立した AES 入力検証はしていません。PID 273 のルート保持も機器レジスター readback ではなく、ソース上の安全判定と記録イベントに基づく確認です。
